# publish

GitHub のリポジトリを公開できる状態にする。作業は次の5つで、この順に進める。

1. 点検（読み取りだけ）
2. 秘密情報・個人情報の検査（読み取りだけ）
3. ファイルの追加と削除
4. README の仕上げと校正
5. GitHub の設定（外から見える変更）

1と2の結果を先に利用者に見せてから、3以降に進む。読み取りだけの段階で全体像を共有すると、何を直すかを利用者が選べるし、後で手戻りが出にくい。

`<SKILL>` は、この SKILL.md があるディレクトリの絶対パス（Claude Code では「Base directory for this skill」）。

## 1. 点検

```bash
bash <SKILL>/scripts/audit.sh <リポジトリのパス>
```

ファイル、CI のワークフロー、GitHub の設定（`gh` でログイン済みなら）を調べ、`OK`／`NG`／`--` のチェックリストを出す。`--` は、リポジトリの用途によって要るかどうかが変わる項目である。用途（ツール、テンプレート、スキル、ポートフォリオなど）を README から読み取り、要るかどうかを判断して利用者に示す。

点検の結果は、そのまま貼らず、`NG` と判断が要る `--` だけを、3〜5のどこで直すかに振り分けて短くまとめる。

## 2. 秘密情報・個人情報の検査

```bash
bash <SKILL>/scripts/scan.sh <リポジトリのパス>
```

現在のファイルとコミット履歴の両方から、鍵・トークン、メールアドレス、実在しうる電話番号、ローカルの絶対パス、消したが履歴に残るファイル、コミットの作者のアドレスを探す。gitleaks が入っていれば、それも使う。

出るのは候補で、誤検出を含む。1件ずつ前後を見て、次のように分ける。

- テスト用のダミー（`"test-key"` など）：問題なし
- 見本のデータ：架空の値にそろえる。メールアドレスは `example.jp`／`example.com`、電話番号は `000-0000-0000` の形。`example.go.jp` のような実在の属性型の名前は避ける。入力形式の例（「例：03-1234-5678」）は、架空の番号に変えるか判断を利用者に聞く
- 本物の秘密情報：まず利用者に伝え、**その鍵を無効にして作り直してもらう**。ファイルから消しても、履歴と、すでに複製された先には残るため、無効にするのが先である。履歴から消すかどうか（`git filter-repo` など）は、利用者に判断してもらう。履歴の書き換えは force push を伴い、取り消せない
- コミットの作者のアドレス：個人のアドレスが出ていることを伝えるだけにする。変えるかどうかは利用者が決める

## 3. ファイルの追加と削除

### 消すもの

- 作業用の文書（PROGRESS.md、調査メモ、移行の作業メモなど）。中に残す価値のある判断や設計があれば、`docs/decisions.md` などに移してから消す。ソースコードのコメントから参照されている文書は消さない
- 使っていないコード、やめた機能、テスト用の一時ファイル
- `.gitignore` で隠していた作業用ファイルの指定（ファイルを消したら指定も外す）

消す前に一覧を利用者に見せる。

### 足すもの

足りないファイルは、同じプラグインの **setup** スキルの手順とテンプレート（`<SKILL>/../setup/`）で足す。setup の SKILL.md を読み、その「2. テンプレートを埋めて置く」に従う。

public にするリポジトリが、すべて OSS とは限らない。自分用のツールを public に置くだけのこともある。そこで、OSS として出す（他の人に使ってもらい、Issue や PR を受け付ける）かを利用者に聞く。OSS にするときだけ、次の3つを `<SKILL>/assets/` のテンプレートで足す。OSS にしないときは足さず、README のライセンスの節、`package.json` の `license`、非公開の脆弱性報告も扱わない。

| 置く先 | テンプレート | リポジトリに合わせること |
|---|---|---|
| `LICENSE` | `LICENSE-MIT` | 年と著作権者。著作権者は `git config user.name` か、利用者の他のリポジトリの LICENSE にそろえる。MIT 以外にしたいかは、足す前に聞く |
| `SECURITY.md` | `SECURITY.md` | 想定している使い方、対象と対象外、owner/repo（`gh repo view --json nameWithOwner` か `git remote`）。公開後の使われ方を考えて「想定している使い方」を具体的に書く（ローカルだけで動かすのか、ネットワークに出すのか） |
| `CONTRIBUTING.md` | `CONTRIBUTING.md` | `{{CHECK_COMMANDS}}` を CI と同じ検査のコマンドにする。画面があるリポジトリなら、スクリーンショットの決まりを足す。AGENTS.md があれば、冒頭に「人間向けの一般規約（IssueやPRの出し方）は[CONTRIBUTING.md](CONTRIBUTING.md)を参照。」を足す |

`package.json` があれば、`name` をリポジトリ名にそろえ、`description`・`repository` を足す。OSS にするなら `license` も足す。

### CI

- テスト・lint・型チェック・ビルドのうち、リポジトリにあるものを CI で回す。CI がなければ足す
- すべてのワークフローの先頭に `permissions:` を置き、`contents: read` か `{}` に絞る。書き込みが要るジョブだけ、ジョブの中で足す。リポジトリの既定の権限が変わっても広がらないようにするため
- `pull_request_target` のワークフローでは PR のコードを checkout しない
- アクションを SHA で固定するかは利用者に聞く（`uses: actions/checkout@<40桁のSHA> # v7` の形）。タグは付け替えられるため固定のほうが安全だが、Dependabot の更新が SHA の PR になる

## 4. README の仕上げと校正

README に次の節があるかを見て、足りないものを書く。

- 冒頭：何をするものか（一文）、誰向けか
- 使い方（インストールから最初の実行まで）
- 動作環境
- 画面があれば画面の写真（最新の画面で撮り直す）
- OSS にするなら、ライセンス（と、使うときの注意があれば）
- テンプレートなど海外の利用者を見込むなら README.en.md

書き終えたら、日本語の文書を docs-rules で校正する。**docs-rules はルールの本文が大きく、スキルを読み込んで手順どおりに進めるとトークンを多く使う。** ここでは `references/docs-polish.md` の軽い手順で校正する。

## 5. GitHub の設定

`references/github-settings.md` のコマンドで設定する。設定は外から見える変更なので、実行する前に、変える項目と値の一覧を利用者に見せて承認を得る。

そろえる設定：

- About：説明、topics、ホームページの URL
- Wiki を無効にする、マージしたブランチを自動で消す
- main の保護（Ruleset：削除と force push の禁止、PR 必須、CI の必須チェック、未解決のレビューのスレッドが残るとマージできない、push で承認が外れる。複数人なら CODEOWNERS で危ない場所に持ち主を決める）。入れると main に直接 push できなくなるため、承認を得るときにそのことを伝え、設定の最後に入れる
- secret scanning と push protection、Dependabot alerts と security updates
- OSS にするなら、非公開の脆弱性報告（SECURITY.md の報告先）
- 用途に応じて：テンプレートリポジトリ、Discussions、GitHub Pages、Release

リポジトリを public にする操作は、利用者がはっきり頼んだときだけ、すべての作業の最後に行う。公開していた間に複製された内容は、非公開に戻しても消えない。

## 進め方と報告

- 3と4の変更は、種類ごとにコミットを分ける（例：`chore: セキュリティポリシーと Dependabot の設定を置く`、`docs: README に動作環境を書く`）。リポジトリのコミットの書き方に合わせる。push は利用者が頼んだときだけ
- 最後に `audit.sh` をもう一度実行し、残った `NG` と、意図して残した項目（理由つき）を報告する
